Architecture Soundness

flag No change management for the four new approval steps
Detail

The shortage worklist introduces four sequential approval steps that change how Buyers, Logistics, PPCP, and Planners work daily. The design doesn't address how these teams will be onboarded or how adoption will be measured.

flag No timeout or escalation if an approval step stalls
Detail

All four approval steps are sequential — if one stalls, the entire shortage case blocks. No turnaround target, escalation path, or fallback is defined. The health dashboard tracks "SLA breaches" but no SLA exists to breach.

worth-checking No plan for when SAP data extraction is late or fails
Detail

Everything runs on hourly SAP data. If extraction misses the 15-minute window before a re-plan slot, it's unclear whether the worklist warns users, freezes cases, or silently serves stale data.

Internal Consistency

flag Phase 1 is called "human-triggered" but most components run autonomously
Detail

The design summary says Phase 1 is human-triggered (3A), but shortage detection, queue ranking, re-plan computation, notifications, and outcome recording all run without human input (3C). Only the SAP transaction shortcut is truly human-triggered.

flag Health dashboard tracks "SLA breaches" — but no SLA is defined
Detail

The monitoring dashboard references service-level targets that don't appear anywhere else in the design — not in the approval steps, not in the worklist, not in the operational agreement.

worth-checking "Named approver at every step" — only the final planning step names one
Detail

The operating agreement promises a named approver at each step, but only the re-plan date approval explicitly requires one. The other three steps assign roles (Buyer, Logistics, PPCP) without requiring a specific named individual.

Business Grounding

flag conflicting €2m expedite-cost savings cited — but no baseline measurement exists
Detail

The value case anchors on ~€2m/yr in avoidable expedite spend, but the customer has never measured this. The baseline is planned as future work. If the validated number is materially lower, the investment case weakens.

flag partially-supported Hourly SAP extraction assumed — but IT governance may block it
Detail

Shifting from nightly batch to hourly delta needs IT approval. Given that even a middleware request takes 6 weeks, there's no reason to assume extraction changes face a lighter path. If this stays nightly, the entire freshness improvement disappears.

worth-checking partially-supported System maintenance team named as owner — but may not exist yet
Detail

The design assigns baseline computation, weekly monitoring, and post-handover ownership to a team whose capacity is flagged as unconfirmed in the risks table. Without this team, the monitoring loop breaks and the system degrades silently.

Worth Asking the Customer

IT Security
The shortage worklist opens SAP transactions pre-filled with PO numbers and dates. Does your security team treat that as an integration channel that needs the same middleware approval as a direct system write?
Why this matters

If IT Security classifies the pre-filled SAP shortcut the same way as a write-back, the initial deployment can only send notifications — no direct action path for planners until middleware is approved.

Finance
The expedite-cost savings target that justifies this project is ~€2m/yr — but that number hasn't been measured yet. Where did it come from, and does the business case hold if the validated baseline is significantly lower?
Why this matters

The entire value story depends on this figure. If Finance signs off on a lower validated number, the scope or approach may need to change.

Head of Planning
The new approval step for re-plan dates adds a formal gate your team doesn't have today. How many of these do you expect per week, how fast should they turn around, and what happens when the approver is unavailable?
Why this matters

Today re-plan decisions happen informally. Adding a formal gate improves traceability but could slow things down if volume, SLA, and escalation aren't agreed upfront.

Director of Ops
The team responsible for maintaining the system after go-live — computing the savings baseline, reviewing data quality weekly, owning the solution long-term — is that an existing team, or does it need to be created?
Why this matters

If this team doesn't exist by go-live, the savings baseline never gets computed, data quality issues go undetected, and nobody owns the system after handover.

Sponsor
Before SAP write-back and richer data sources come online, the system delivers a shortage worklist with pre-filled SAP shortcuts and notifications. Is that initial scope valuable enough on its own to justify deployment?
Why this matters

The higher-autonomy features (automated SAP updates, MES data, copilot assistance) are all later phases. The sponsor should confirm Phase 1 alone moves the needle.

These are prompts for your judgment, not fixes — take or leave any of them.
